moon v2.6 - Cleanup and wait task dependencies, OpenTelemetry metrics, Pkl type checking, and more

October 5, 2026 · 16 min read
Miles Johnson
Founder, developer

This release is all about what happens around your tasks. Dependencies can now run after a task to clean up after it, or alongside it as a long-running sidekick. Persistent tasks no longer wait in line until the very end of the pipeline. Tasks can expect to fail, and override the shell's environment. The OpenTelemetry integration from last release now emits metrics, and Pkl configs can finally be type checked.

Task improvements​

The first round of changes apply to tasks and their options.

Cleanup and wait dependencies​

Task deps have always meant one thing: "run this before me, and make sure it passes". That's perfect for builds and code generation, but it falls apart the moment a task needs something to be running (a database for integration tests, a server for end-to-end tests) and then needs it gone again afterwards. Until now, that usually meant a shell script that starts everything in the background, traps a few signals, and hopes for the best.

In v2.6, dependencies support a new type setting, which controls when the dependency runs in relation to the task:

  • required (default) - Runs before the task, and must complete successfully. Exactly what you're used to.
  • cleanup - Runs after the task has ran its command, even when the task fails. Ideal for tearing things down, like stopping a database or removing temporary files.
  • wait - Runs before the task, but the task only waits for the dependency to start running, not to complete. Ideal for long-running dependencies, like a server that the task sends requests to.

Put them together, and an entire end-to-end testing workflow fits into a single task:

moon.yml
tasks:
  e2e:
    command: 'playwright test'
    deps:
      # Start the database, and wait for it to complete
      - 'db:start'
      # Start the server, and run the tests alongside it
      - target: 'web:serve'
        type: 'wait'
      # Stop the server and database once the tests have ran, pass or fail
      - target: 'web:stop'
        type: 'cleanup'
      - target: 'db:stop'
        type: 'cleanup'
    options:
      # Don't hydrate from the cache, as the server would be stopped right after it started
      cache: false

A few things worth knowing about how these behave:

  • Cleanup dependencies run once the task has ran its command, whether it passed or failed, and even when a failure aborts the pipeline. They're skipped when there's nothing to clean up, like when the task was hydrated from the cache, unless the task has already started a wait dependency, since stopping it is usually the cleanup's whole job.
  • Wait dependencies only need to have started, which isn't the same as being ready. If your server takes a moment before it accepts connections, poll a health check before sending requests.
  • Wait dependencies are not stopped once the task completes, so pair them with a cleanup dependency that stops them, as seen above.
  • Wait dependencies can be persistent, and they don't count towards the pipeline's concurrency limit, so they never block the tasks waiting on them.
  • Wait dependencies are still subject to runInCI: a task that runs in CI can't wait on one that doesn't. Since servers don't run in CI by default (tasks named serve are persistent automatically), enable runInCI for web:serve in the example above. See persistent tasks in CI below.
  • Since neither type completes before the task runs, they don't contribute to the task's hash, and they always run their command instead of being hydrated from the cache.

Cleanup dependencies also work great with task inheritance. For example, any project can define a teardown task that runs after its other tasks, without each task having to opt-in individually. And don't worry, the teardown task won't try to clean up after itself!

.moon/tasks/all.yml
implicitDeps:
  - target: '~:teardown'
    type: 'cleanup'
    optional: true
caution

Cleanup dependencies are not ran when the pipeline is interrupted by a signal, like pressing Ctrl+C.

Expected failures​

The allowFailure task option is handy for advisory checks, but it's often reached for in a different situation: a check that's known to be broken, like after enabling a stricter compiler or lint rule midway through a migration. Once the failures are fixed, nothing tells you, so the option lingers, and future regressions slip through unnoticed.

In v2.6, the new expectFailure task option covers this case. The task must fail, and once it passes, the pipeline fails with an error asking you to remove the setting.

moon.yml
tasks:
  typecheck:
    command: 'tsc --build'
    options:
      expectFailure: true

Unlike allowFailure, an expected failure is treated as a success, so other tasks can depend on it, like bundling the JavaScript that tsc still emits. A few more details:

  • Only a failure of the command itself is expected. A command that couldn't run (exit code 126 or 127), or was killed by a signal, fails as normal, so a typo can't pass as the expected failure.
  • The task is never cached, and isn't retried, so a fix is noticed on the very next run.
  • It can't be combined with allowFailure or persistent.

Overriding system environment variables​

Since v2, variables set in your shell or CI take precedence over a task's env, so that KEY=value moon run ... works as you'd expect. That's the right default, but sometimes a task needs a specific value regardless, like NODE_ENV=test for tests, while CI exports NODE_ENV=production.

In v2.6, the new envOverride task option lets the task's variables win instead, either for all of them, or only those listed.

moon.yml
tasks:
  test:
    command: 'jest'
    env:
      NODE_ENV: 'test'
      TZ: 'UTC'
    options:
      envOverride: ['NODE_ENV', 'TZ'] # or `true`

Variables loaded with envFile are not overridden, and neither is PATH, as that would remove the paths of toolchains. To keep a specific variable configurable from the shell, fall back to it with substitution, like LOG_LEVEL: '${LOG_LEVEL:-info}'.

Output style from the command line​

The outputStyle task option controls how a task's output is displayed, but it's configured per task, and it doesn't apply to primary targets (those you explicitly requested on the command line). That's a sensible default locally, but in CI, you typically want the opposite: successful tasks should stay quiet, while failures print in full.

In v2.6, moon run, moon ci, moon check, and moon exec support a new --output-style option, which overrides the style for all tasks in that run. Since it was requested explicitly, it also applies to primary targets.

$ moon ci :test :lint --output-style buffer-only-failure --summary minimal

Interactive tasks are the exception, as they must remain attached to the terminal, and always stream their output.

Prefer to configure it once? The new explicitTaskOutputStyle experiment applies each task's configured outputStyle to primary targets as well.

.moon/workspace.yml
experiments:
  explicitTaskOutputStyle: true

Persistent tasks run within the pipeline​

Persistent tasks (servers, watchers, anything that never exits) have always been tricky in a dependency graph. Our answer since v1.6 has been to collect them all, and run them last as a single batch, once every other action in the pipeline had finished. It worked, but it also meant your dev server sat around waiting on completely unrelated tasks before it was allowed to boot.

In v2.6, persistent tasks run as soon as they're reached in the action graph, like any other task. They still run in parallel and never block the actions that come after them, but they now start as soon as their own dependencies have completed, and a persistent task no longer holds up the persistent tasks that depend on it.

# The servers start as soon as they're ready, while docs continue to build
$ moon run api:dev web:dev docs:build

And since a non-persistent task can now wait for a persistent task to start, servers can finally be used as dependencies of regular tasks, instead of only of other persistent tasks.

Persistent tasks in CI​

We also took a hard look at how persistent tasks behave in CI, as a task that never completes is a great way to keep a pipeline running until it times out. Persistent tasks now never run in CI by default, even when they define outputs, or have a type of build or test. When you need one in CI, like a server for end-to-end tests, explicitly enable runInCI.

moon.yml
tasks:
  serve:
    command: 'vite preview'
    options:
      persistent: true
      runInCI: true

Even then, it's only ran for the tasks that depend on it, or when explicitly passed as a target, and never on its own. So moon ci will start the server for your e2e task, but it won't start it just because a file in the project changed. The same goes for moon check, which now only runs persistent tasks when another task depends on them, instead of never completing.

And if you forget to enable it, the run_in_ci_mismatch error (a task that runs in CI depends on a task that doesn't) now explains exactly how to resolve it.

A faster pipeline​

To make all of this possible, we rewrote the action pipeline's job dispatcher, and made it 10-15x faster while we were in there. Dependency relationships are now extracted from the action graph once up front, and completed jobs unblock their dependents incrementally, instead of re-traversing the graph every time the dispatcher checks what's next. Additionally, interactive tasks now only block the pipeline until they themselves have completed, instead of until every task that was already running has completed.

OpenTelemetry metrics​

In v2.5, we shipped OpenTelemetry support for traces and logs, with a little disclaimer that metrics were supported, but that we didn't emit any yet. Well, now we do! When --otel (or MOON_OTEL) is enabled, moon records metrics for every task, action, and operation that runs within the pipeline.

MetricInstrumentDescription
moon.task.runsCounterNumber of tasks ran within the pipeline.
moon.task.durationHistogramDuration of tasks in milliseconds.
moon.action.executionsCounterNumber of actions executed within the pipeline.
moon.action.durationHistogramDuration of actions in milliseconds.
moon.operation.executionsCounterNumber of operations executed within an action.
moon.operation.durationHistogramDuration of operations in milliseconds.

Task metrics are the ones to reach for when building dashboards, as they're labeled with the target, project, task, toolchains, status, and whether the task was flaky (passed only after a retry). That means you can finally graph questions like "how long does build take across the entire workspace?", "which project is the most expensive in CI?", or "what's our cache hit rate this week?" (compare the cached and cached-from-remote statuses against the total).

Action and operation metrics go one level deeper. Actions cover the pipeline as a whole (syncing projects, setting up toolchains, installing dependencies), while operations are the individual steps within an action, like generating a hash, hydrating outputs from the cache, or executing the command. Operations are purposefully not labeled by target or project, to keep cardinality in check; traces provide that level of detail instead.

$ export OTEL_EXPORTER_OTLP_ENDPOINT="http://localhost:4318"
$ moon --otel ci
caution

Since the target attribute is recorded for every task that runs, the cardinality of the moon.task.* and moon.action.* metrics scales with the number of tasks in your workspace. If your observability backend complains, drop or aggregate away the attribute within your OTEL collector.

Type checking for Pkl configs​

Pkl has been a supported configuration format since v1.29, but until now, moon was the only one that knew what a valid config looked like, and you'd only find out about a typo once moon loaded the file. In v2.6, every configuration file has a Pkl module that types its settings, which is generated to .moon/cache/schemas/pkl (when pkl is installed), right alongside the JSON schemas.

A config that amends its module is type checked by Pkl itself, which reports unknown settings and invalid values when the config is evaluated. And editors with Pkl support, like the VS Code extension, now provide completion and documentation for every setting.

.moon/workspace.pkl
amends "./cache/schemas/pkl/WorkspaceConfig.pkl"

projects = List("apps/*", "packages/*")

For project configs, a triple-dot URI resolves the module by searching each parent directory in turn, so the same line works for a project at any depth (except the workspace root itself, which uses a ./ path).

moon.pkl
amends ".../.moon/cache/schemas/pkl/ProjectConfig.pkl"

tasks {
  ["build"] {
    command = "vite build"
    deps = List("^:build")
  }
}

Toolchains and extensions are configured by plugins, whose settings can't be known ahead of time, so .moon/toolchains.pkl and .moon/extensions.pkl should extends their modules instead, which allows additional settings. View the official documentation for the full rundown, including how to create settings that accept multiple shapes.

Toolchain environment activation​

Some tools need more than a binary on PATH to work correctly. Java expects JAVA_HOME, package managers want to know where globals live, and so on. proto has handled this for a while through the activate_environment plugin function (the same one that powers proto activate), but moon never called it, so tasks ran with a less complete environment than your shell did.

In v2.6, when moon builds a command (for tasks and toolchain operations), the environment of each toolchain that has been setup is now activated. This may set environment variables, and prepend directories to PATH, exactly as proto would. We were careful to keep this from stepping on your toes though:

  • Variables that are already configured, like a task's env, are never overridden.
  • When a task has multiple toolchains, the first configured toolchain takes precedence.
  • Only toolchains that have actually been setup are activated, as their tool directory wouldn't exist otherwise.

For plugin authors, activate_environment is now listed as a tier 3 function in moon toolchain info.

Remote cache retries​

When using an HTTP based remote cache, a single failed request (like a 503 from a CDN under load) would fail the entire task with missing outputs, even though trying again would have succeeded. In v2.6, requests that fail with a transient error (connection failures, timeouts, and 5xx, 408, or 429 responses) are now retried up to 3 times, with exponential backoff. The amount can be customized with the new remote.cache.retryCount setting, or 0 to disable retries.

.moon/workspace.yml
remote:
  api: 'http'
  host: 'https://your-host.com'
  cache:
    retryCount: 5

Furthermore, if the remote host is unreachable when moon first connects to it, the remote cache is now disabled for that run, instead of every request failing (and retrying) on its own.

Upgrade notes​

A few changes in this release may be noticeable when upgrading, so we want to call them out directly.

  • Some caches will be invalidated once. A task's resolved toolchains list was previously ordered by an internal hash set, instead of by what was configured. It's now deterministic (configured toolchains first, followed by the toolchains they require), which also fixes the $taskToolchain token. Since this list is part of a task's hash, tasks that run against multiple toolchains (like node and npm) will miss the cache on their first run after upgrading.
  • Persistent tasks no longer run in CI by default, even when they define outputs or a type of build or test. See persistent tasks in CI above.
  • moon check exits with a non-zero code when there's nothing to check, instead of prompting for tasks to run (or failing in non-TTY environments).
  • JSON output uses the documented keys. Project configuration within JSON output (moon project --json, moon query projects, MCP responses, and webhook payloads) serialized some renamed settings under the wrong keys. They now match the JSON schemas and @moonrepo/types: type instead of typeOf, runInCI instead of runInCi, and $schema instead of schema. If you have scripts that parse this output, double check them!
  • deps.*.env no longer overrides system variables. A dependency's env was applied along with moon's built-in variables, so it took precedence over variables set in the shell or CI, contrary to the documented order. It's now only set when the variable is missing, like a task's env, unless the dependency enables envOverride.
  • The MCP server now requires the 2026-07-28 protocol. moon mcp has moved to the stateless MCP protocol, so older protocol versions (2025-11-25 and below) and the initialize handshake are no longer supported. Make sure your MCP client is up to date.

Other changes​

View the official release for a full list of changes, but here's a few more worth calling out:

  • Updated runDepsInParallel (when disabled) to skip persistent dependencies when ordering the dependencies that follow them, as a persistent dependency never completes.
  • Updated moon sync config-schemas to also generate the new Pkl modules.
  • Added an args setting to toolchain bins entries, for passing additional arguments to the install command, like feature flags. Support depends on each toolchain.
  • Moved hash manifests out of .moon/cache/hashes, and into the local content-addressable cache as blobs. As such, the local cache backend is now always enabled, while storing task outputs in it remains gated by the casOutputsCache experiment.
  • Updated proto to v0.62.2 from 0.60.2, which includes Swift support and immutable lockfiles, and community plugins and Zig support.

What's next for moon?​

This release took much longer than expected due to the extensive changes and improvements made to the action pipeline and task dependencies. As such, we had time to reflect on the overall design and architecture of the pipeline and its surrounding systems, and have come to the conclusion that it needs a rework if we are to extend it further.

Because of this, v2.6 will be the last release of the year, as we want to spend the remaining time focusing on v3.0 and what improvements we can bring. So far, we have the following planned:

  • Redesign of the action graph and pipeline
  • Reevaluate graph relationships (upstream and downstream)
  • Resolve experimental features
  • Next-generation tokens (v2)
  • VCS plugins
  • Node-based graph caching
  • New website and documentation (first-class LLM support)
  • And much more!
