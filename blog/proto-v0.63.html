proto v0.63 - Trusted configs, Kotlin support, and schema plugins v2

October 6, 2026 · 16 min read
Miles Johnson
Founder, developer

This release is all about trust. Configuration files now have to earn it before they can touch your shell. Elsewhere, Kotlin joins the toolchain, non-WASM plugins get a brand new format, proto pin finally writes to the file you'd expect, and lockfiles learn the difference between Alpine and Debian.

Trusted configurations​

A .prototools file looks harmless. A few versions, maybe an alias or two. But it's capable of a lot more than that, and shell activation applies all of it the moment you change directories. Consider a repository you cloned 5 seconds ago, that ships with this:

.prototools
node = "24"

[env]
BASH_ENV = "./scripts/totally-normal.sh"

With activation enabled, BASH_ENV is exported into your shell as soon as you enter the directory, and the very next Bash process you spawn runs the script. The same goes for PROMPT_COMMAND, [shell.aliases] that quietly shadow your everyday commands, third-party plugins that are downloaded and executed, and settings like url-rewrites that redirect where tools are downloaded from. You didn't run anything. You just looked at someone's code.

So starting with this release, local configuration files must be trusted before their security-sensitive settings are applied.

$ proto trust

What requires trust?​

The settings that can execute code, or change what code gets executed, are considered security-sensitive:

  • [env] (including .env files), [shell], [plugins], and [backends.*].
  • [tools.*], except for version aliases.
  • The proto version pin, and pins for tools that aren't built-in (like community plugins and the asdf backend), as loading them downloads and executes a third-party plugin.
  • Every [settings] entry, except for detect-strategy, pin-latest, telemetry, and unstable-lockfile.

Everything else is always applied. Version pins for built-in tools (and the npm and cargo backends), version aliases, and the harmless settings continue to work exactly as before. Cloning a repository and running Node.js still gets you the right version, no ceremony required.

Trusting and untrusting​

proto trust accepts a directory (defaulting to the current one), which trusts every configuration within it and its sub-directories, or a path to a single configuration file. Either way, proto prints the security-sensitive settings that it's about to apply, so you can review exactly what you're agreeing to.

# This project, and everything within it
$ proto trust

# Just this one file
$ proto trust ./tools/.prototools

Trust is recorded against the path, not the file's contents, so editing your own configuration never requires re-trusting it. The flip side is that changes you pull into a trusted repository are trusted too, so give .prototools diffs the same review you'd give any other code.

Changed your mind? proto untrust removes it, and will tell you if the configuration is still trusted through another source, like a trusted parent directory. And since records are path based, proto clean trust removes records for paths that no longer exist, so a different repository cloned to the same location later on doesn't inherit trust it never earned. This also runs as part of a regular proto clean.

Who doesn't need to do anything?​

We wanted this to stay out of your way wherever possible, so a few configurations are trusted automatically:

  • Your own. The ~/.prototools and ~/.proto/.prototools files are owned by you, and are always trusted.

  • CI. The checked out repository is the code being built, and there's no one around to type proto trust, so every configuration is trusted in CI. It's detected from the CI environment variable (or a provider's specific variables), so if you've exported it in your shell profile for some reason, now's a great time to stop. proto diagnose will nag you about it if you don't.

  • Trusted paths. Directories listed in the PROTO_TRUSTED_PATHS environment variable (separated the same way as your system path) are trusted wholesale. Handy if all of your own work lives in one place.

    export PROTO_TRUSTED_PATHS="$HOME/work"

  • Settings proto wrote for you. When proto adds security-sensitive settings to a configuration that had none, for example with proto plugin add, the file is trusted automatically. You asked for the plugin, after all.

Never silent​

An ignored setting is only safe if you know it was ignored, so proto tells you about untrusted configurations everywhere it reasonably can.

proto activate warns about each untrusted configuration once per shell session (not on every prompt, we promise). Most other commands log a warning too, except for run, exec, bin, shell, and shims, since those are executed constantly by scripts and editors. proto status lists untrusted configurations above its table, proto diagnose reports them as warnings, and proto debug config labels them.

And if a tool's plugin is configured in an untrusted file, proto refuses to load that tool, instead of quietly substituting a built-in or community plugin with the same name. Getting a different tool than the one the configuration asked for would be its own kind of surprise.

Head over to the trust documentation for all of the details.

Kotlin support​

Hot on the heels of Zig in v0.62, Kotlin joins proto's built-in toolchain, making it our second JVM language after Java landed in v0.59.

$ proto install java
$ proto install kotlin

The plugin installs JetBrains' portable command-line compiler, and provides the kotlin and kotlinc executables. Kotlin runs on the JVM, so a Java runtime is required as well. The Kotlin launchers look for JAVA_HOME first, which proto's Java plugin sets when activated, so pinning both tools is all it takes.

Versions are detected from .kotlin-version files, and from the Kotlin entry in .sdkmanrc files, so projects already using SDKMAN! are picked up without any proto-specific configuration. Releases all the way back to before 1.0 are supported, as are release candidates and EAP builds when requested explicitly.

Kotlin support is still unstable, so please report any issues you run into! Kotlin/Native is a separate distribution, and is not installed by this plugin.

Pinning to the closest configuration​

Here's a small one that has bugged us for a while. Run proto pin node 24 from a directory deep within your project, say a components folder 4 levels down, and proto would dutifully create a brand new .prototools file... right there in the components folder. Technically correct, practically never what you wanted.

We've added a new closest location, which traverses upwards from the current directory, and targets the first directory that has a configuration file. If none is found, the current directory is used, just like before.

~/Projects/app/.prototools         <- pinned here
~/Projects/app/packages/web/src    (cwd)

This is now the default for proto pin, proto unpin, proto alias, proto unalias, proto plugin add, proto plugin remove, and proto install --pin (and the MCP install_tool tool). Directories that only have an environment configuration (.prototools.<env>) are skipped, and your user and global configurations are never targeted — pass --to user or --to global for those. It can also be used with the pin-latest setting.

.prototools
[settings]
pin-latest = "closest"

If you prefer the old behavior, pass --to local (or --from local).

libc-aware lockfiles​

Lockfile records have always been keyed by operating system and architecture. That's enough for macOS and Windows, but on Linux, plenty of tools publish separate artifacts for glibc and musl, each with its own checksum. So a Debian laptop and an Alpine CI container would happily share a single record for Linux on x64, and then fail each other's checksum verification.

Records created on Linux now include a libc field, recording whether the machine uses GNU or musl.

.protolock
[[tools.node]]
os = "linux"
arch = "x64"
libc = "musl"
spec = "24"
version = "24.9.0"
checksum = "sha256:..."

No migration is required. Existing records without a libc continue to match every libc, and are backfilled with the current libc the next time an install updates the record. When another libc has locked a version, but yours hasn't, the version is inherited the same way it already is for other operating systems and architectures.

Stricter immutable lockfiles​

Speaking of inheritance, this one is important. In v0.62.2, we started inheriting a version locked by another platform when the current platform had no record. That's the right call for a regular install, as a resolved version applies to every machine.

It was the wrong call for --immutable-lockfile. The other platform's checksum isn't valid for your download, so the tool was being installed without ever being verified against the lockfile — the exact guarantee that flag exists to provide. It now fails instead.

Lockfile is immutable, but is missing a record for node 24 on x64-linux-musl. Only other platforms
have locked this version, so the download cannot be verified.

To fix it, run proto install (without the flag) once on each platform you install on, and commit the updated lockfile. Installs without --immutable-lockfile continue to inherit as before.

Schema plugins v2​

Not every tool needs a WASM plugin. For the common case — download an archive, extract a binary — proto supports non-WASM plugins: a JSON, TOML, or YAML file that describes the tool. They power the entire community registry, in fact.

But the format grew its own vocabulary over the years, like download-file, manifest-url, and version-files, which drifted away from the WASM plugin API. Worse, it had no way to express the most common real-world wrinkle: a tool that changed something between releases. Renamed an asset in 2.0? Moved hosts in 3.0? Your options were dropping old versions, or rewriting the plugin in WASM.

Format v2 fixes both. Opt in with format = "2", and each section maps directly to the output of a WASM plugin function, with snake_case keys everywhere: metadata is the output of register_tool, install is the output of download_prebuilt, locate is the output of locate_executables, and so on. If you've read the API documentation, you already know the settings.

And for tools that change over time, there's [[overrides]].

protostar.toml
format = "2"

[metadata]
name = "Protostar"
type = "command-line"

[resolve]
git_url = "https://github.com/moonrepo/protostar"

[install]
download_url = "https://github.com/moonrepo/protostar/releases/download/v{version}/{download_name}"

[platform.linux]
download_name = "protostar-{arch}-unknown-linux-{libc}.tar.gz"

[platform.macos]
download_name = "protostar-{arch}-apple-darwin.tar.xz"

# 2.0 renamed the Linux asset, and dropped arm64
[[overrides]]
range = ">=2"

[overrides.platform.linux]
download_name = "protostar-v2-{arch}.tar.gz"
archs = ["x64"]

# Nightlies live somewhere else entirely
[[overrides]]
range = "canary"

[overrides.install]
download_url = "https://example.com/protostar/nightly/{download_name}"

Each override targets a version range (or canary releases), and can replace download, executable, platform, and even version resolution settings, so releases from before a project changed its tag format can be parsed with their own pattern. Every matching override is applied in order, with later ones winning, and pre-releases match the range of their release, so a release candidate for 2.0 picks up the 2.x settings too.

A few more niceties came along for the ride. Unknown fields are now an error, so a typo no longer silently does nothing. URLs can reference the platform's resolved names with the {download_name} and {checksum_name} tokens, which error if the current platform has no name configured, instead of quietly producing a broken URL. And source.latest can pin the latest version, instead of always using the highest stable one.

Format v1 isn't going anywhere, and existing plugins continue to work as-is.

View the format v2 documentation for the full list of settings.

WASM API changes​

load_git_tags returns errors​

The load_git_tags function used to swallow failures and return an empty list. Which sounds harmless, until you realize every plugin then reported a confusing "Failed to resolve version" error, while the real cause — an unreachable remote, a missing credential, an unaccepted Xcode license on macOS (yes, really) — was nowhere to be seen. It also meant previously cached versions were never used as a fallback.

It now returns an error that includes the exit code and stderr of git ls-remote. If your plugin should continue without the tags, handle the error explicitly.

let tags = load_git_tags("https://github.com/org/repo").unwrap_or_default();

HostPlatform​

The new HostPlatform type represents an architecture, operating system, and libc as a single value. It parses from proto's own <arch>-<os>[-<libc>] format, and from Rust target triples, and converts back to a target triple with to_rust_platform. Since so many tools name their release artifacts after target triples, this makes mapping them much less tedious.

let platform = HostPlatform::parse("aarch64-unknown-linux-musl")?;

platform.arch; // HostArch::Arm64
platform.os; // HostOS::Linux
platform.libc; // HostLibc::Musl
platform.to_string(); // "arm64-linux-musl"
platform.to_rust_platform(); // "aarch64-unknown-linux-musl"

We also updated HostLibc to treat unsupported values as unknown, instead of failing to deserialize, so plugins built against this version keep working when a future proto release adds a libc.

Testing other platforms​

The ConfigBuilder::host test utility now requires a HostPlatform, instead of an operating system and architecture, so the libc can be configured too. The libc is no longer detected from the current machine, and defaults to GNU on Linux, so tests behave the same on every machine.

let plugin = sandbox
    .create_plugin_with_config("id", |config| {
        config.host(HostPlatform::parse("x64-linux-musl").unwrap());
    })
    .await;

Breaking changes​

  • The security-sensitive settings of local .prototools files are ignored until the file is trusted. Run proto trust in your projects, or set PROTO_TRUSTED_PATHS. CI environments are unaffected.
  • Version pins for tools that aren't built-in, including community plugins and the asdf backend, also require trust.
  • proto pin, unpin, alias, unalias, plugin add, plugin remove, and install --pin now write to the closest configuration file, instead of the one in the current directory. Pass --to local (or --from local) for the previous behavior.
  • proto install --immutable-lockfile now errors when only other platforms (including other libcs) have locked a version.
  • WASM API: load_git_tags returns an error when the tags fail to load, instead of an empty list.
  • WASM API: ConfigBuilder::host requires a HostPlatform, instead of an operating system and architecture.

Other changes​

View the official release for a full list of changes.

  • Executable paths in non-WASM plugins now support tokens, like {version}, for secondary executables too, not just the primary executable.
  • Plugin downloads (from OCI registries, GitHub, and URLs) are now always attempted, even when the hosts used to detect an internet connection are blocked or slow. The connection check is only used to explain a failed download, which now includes the underlying error. VPN users, rejoice.
  • Updated Rust to v1.99.0.
