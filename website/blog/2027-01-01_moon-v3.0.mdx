## Resolved experiments

Over the last few releases, we've rebuilt moon's hottest code paths and its local cache, reworked
how task output is displayed, and shipped these changes behind
[experiments](/docs/config/workspace#experiments), most of which were enabled by default in v2.5.
They've since proven themselves, so in v3, the following experiments have been resolved. Their
implementation is now the _only_ implementation, the previous one has been removed, and the setting
no longer exists.

- `asyncAffectedTracking` (added in v2.2) - Affected projects and tasks are now always tracked
  asynchronously, and the synchronous tracker has been removed.
- `asyncGraphBuilding` (added in v2.2) - The project and task graphs are now always built
  asynchronously, and the synchronous builder has been removed.
- `casOutputsCache` (added in v2.3) - Task outputs are now always stored in the local
  content-addressable cache, and the tarball-based cache has been removed.
- `explicitTaskOutputStyle` (added in v2.6) - A task's `outputStyle` option is now always applied,
  including to primary targets, which previously ignored it and always displayed their output.
- `nativeFileHashing` (added in v2.3) - Files are now always hashed natively within moon's task
  pool, and hashing files through the VCS has been removed.

Since configuration is strictly validated, moon will fail to load a workspace that still configures
a resolved experiment, so be sure to remove it.

```diff title=".moon/workspace.yml"
 experiments:
-  asyncAffectedTracking: true
-  asyncGraphBuilding: true
-  casOutputsCache: true
-  explicitTaskOutputStyle: true
-  nativeFileHashing: true
```

Their `MOON_EXPERIMENT_*` environment variables, like `MOON_EXPERIMENT_ASYNC_AFFECTED_TRACKING`, no
longer have any effect. If you had disabled one of these experiments to work around an issue,
please [report it](https://github.com/moonrepo/moon/issues), as it can no longer be disabled.

If you had disabled `asyncGraphBuilding` because of a dependency cycle error, the cycle itself is
the problem, as the synchronous builder would silently drop some of the edges that formed it. Break
the cycle, or move one of its edges to a different dependency scope, so that it crosses the
production and development [scope partitions](/docs/how-it-works/project-graph#scope-partitions),
which is allowed.

### Content-addressable local cache

Since v1.30, moon's remote cache has stored task outputs in a content-addressable storage (CAS)
format, while the local cache archived them as `.tar.gz` tarballs. In v2.3, we introduced a local
CAS layer behind the `casOutputsCache` experiment, which stores outputs in the same format as the
remote cache, and over the following releases, we moved archiving and hydration into the
[daemon](/docs/guides/daemon), and hash manifests into the CAS.

In v3, the local CAS is now the _only_ local cache, and tarballs are gone. Unlike most of the
resolved experiments, this one was opt-in, so if you hadn't enabled it, this is a change in
behavior:

- Outputs are stored as deduplicated blobs, so identical files produced by multiple tasks, or by
  multiple runs of the same task, are only stored once.
- Outputs downloaded from a remote cache hit are also stored locally, so the next run hydrates from
  the local cache instead of downloading them again.
- The [`cache.unstable_sharedWorktreeCache`](/docs/config/workspace#cache) setting, which shares the
  cache between all worktrees of a repository, no longer requires an experiment.

When upgrading, the legacy `.moon/cache/hashes` and `.moon/cache/outputs` directories are
automatically removed. Previously archived outputs are not migrated, so the first run of each task
after upgrading will miss the local cache, unless its outputs are in your remote cache.

### Task output styles

The [`outputStyle`](/docs/config/project#outputstyle) task option controls how a task's output is
displayed, but until now, it only applied to transitive targets (those run as a dependency of
another task). Primary targets (those you explicitly requested on the command line) ignored it, and
always displayed their output, so the same task could display its output differently, depending on
how it was run. In v2.6, we introduced the `explicitTaskOutputStyle` experiment, which applies the
option to primary targets as well.

In v3, the option is applied to _all_ targets. Like `casOutputsCache`, this experiment was opt-in,
so if you hadn't enabled it, a primary target that configures `outputStyle` will now display its
output accordingly, both when it runs and when it's hydrated from the cache. For example, a task
with `buffer-only-failure` no longer displays any output when it passes, even when run directly.

```yaml title="moon.yml" {5}
tasks:
  test:
    command: 'vitest'
    options:
      outputStyle: 'buffer-only-failure'
```

```shell
# v2: Always displays the output
# v3: Only displays the output when the task fails
$ moon run app:test
```

To change how output is displayed for a single run, pass the `--output-style` option, which still
takes precedence over the task option, for primary and transitive targets alike.

```shell
$ moon run app:test --output-style stream
```

If a [persistent task](/docs/concepts/task#persistent), like a dev server, configures a style other
than `stream`, its output is now captured even when run directly, and is only displayed once it
exits. [Interactive tasks](/docs/config/project#interactive) are still the exception, as they must
remain attached to the terminal, and always stream their output.

## Performance improvements

With the experiments resolved, we no longer have to keep two implementations of the same code path
in lockstep, which freed us up to profile and optimize the remaining one.

### Affected tracking

Affected tracking (used by `--affected`, `moon ci`, and the action graph) is now **up to 100x
faster** in large workspaces. In our benchmarks, tracking 1,000 tasks went from 715ms to 6.5ms, and
tracking 1,000 projects went from 3.5ms to 0.2ms.

The single largest cost turned out to be compiling glob sets, which took ~175µs per task, and every
task compiled its own, even though most tasks share the same globs through inheritance and
defaults. Compiled glob sets are now cached and shared between tasks, and each changed file is only
matched against each distinct glob set once. On top of that:

- Tasks and projects that were found to not be affected are no longer checked a second time when
  building the action graph.
- Relationships are walked once from every affected task and project, instead of once _per_ affected
  task and project, which was quadratic for deep dependency chains.
- Projects are indexed by their source directory, so each changed file only looks up its ancestor
  directories, instead of every project scanning every changed file.
- Changed files matched by content (the `content` input setting) are read once, instead of once per
  task.

### File hashing

Hashing task inputs is now **~25% faster** on a cold run, and **~5x faster** for files that have
already been hashed. In our benchmarks, hashing 1,000 files went from 13.4ms to 10ms, and to 2.5ms
when their hashes are reused.

Previously, every task hashed all of its inputs from scratch, so a project's `build`, `test`, and
`lint` tasks would each read the same files, and workspace-wide files like lockfiles were read by
every task. File hashes are now memoized for the duration of the process, and reused as long as the
file's size and modification time are unchanged. This is the same strategy Git uses for its index,
including its safeguard for recently modified files, which are never memoized, so that file systems
with coarse timestamps can't serve a stale hash.

Files are also now hashed by a fixed pool of workers, instead of spawning a task per file, and each
file is stat-ed once instead of twice.

### Project and task graphs

Building the project and task graphs is now **~3x faster**, and far more consistent. In our
benchmarks, building the graphs for 1,000 projects went from 260ms to 86ms on average, and in a real
1,000 project workspace, a `moon project` command went from 335ms to 225ms.

The bigger win is consistency. Previously in that same workspace, whenever the graphs had to be
rebuilt, 1 in 8 commands took over a second, and the slowest took 1.9s. While building, every task
asks its toolchains whether they apply to it, and looking up a loaded plugin took an exclusive lock,
so the projects being built in parallel had to take turns. On a busy machine, one slow handoff would
stall everything queued behind it. These lookups now take a shared lock, and the slowest command
went from 1.9s to 331ms. We then fixed the same problem in proto v0.63.1, where calling a plugin
function with a cached result also took an exclusive lock. Under CPU contention, the slowest builds
in our 1,000 project benchmark went from 500ms to 310ms, and builds that took over twice the median
went from 11 to 1 (across 400 builds). On top of that:

- Git information (the branch, revision, and repository) is loaded in the background while the
  graphs are built, instead of one command after another once they were built.
- Projects and tasks are moved into the final graphs, instead of being cloned.
- Dependency cycles are checked once per scope partition, after all relationships have been added,
  instead of once for every relationship.
- Project configs are loaded on a thread pool bounded to the number of CPUs, instead of on a thread
  per project.

The cached workspace graph is also **less than half the size**, going from 4.8MB to 2MB for 1,000
projects. Projects now only store the paths of the `.moon/tasks` configs they inherited from,
instead of a copy of each config, data that's only needed while building the graphs is no longer
cached, and task options are omitted when they're the default value. The cache is also written
atomically, so if moon is interrupted while saving it, the next run rebuilds the graphs, instead of
loading an outdated one.

## Other changes

View the [official release](https://github.com/moonrepo/moon/releases/tag/v3.0.0) for a full list
of changes, but here's a few more worth calling out:

- When projects and tasks are serialized to JSON, like in `moon project --json`, `moon task --json`,
  and `moon query projects|tasks`, fields that are the default value are now omitted, which makes
  task options ~90% smaller. A missing field is its default value, and the `@moonrepo/types` types
  have been updated to match. A project's `inherited` field is also only included by
  `moon project --json` now, while other output includes a new `inheritedFrom` field instead, which
  lists the paths of the `.moon/tasks` configs the project inherited from.
- Project [constraints](/docs/config/workspace#constraints) are now enforced for every relationship
  between 2 projects. Previously, when a project depended on another more than once (like by its ID
  and an alias) with different scopes, only one of those relationships was checked, so a layer or
  tag violation could go unreported, and will now fail.
- moon now uses proto v0.63, which only applies the
  [security-sensitive settings](/docs/proto/config#security-sensitive-settings) of a local
  `.prototools`, like `[env]`, `[plugins]`, and `[tools.*]`, once the config has been
  [trusted](/docs/proto/config#trust). As moon already runs your workspace's tasks, configs within
  the workspace are always trusted, while other local configs, like one in a parent directory, must
  be trusted with [`proto trust`](/docs/proto/commands/trust).
